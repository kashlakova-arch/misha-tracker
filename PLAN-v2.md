### 0.2. Переезд на IndexedDB (решение принято — делаем в шаге 1)

`localStorage` (~5 МБ) снимается как хранилище: приложение уже принимает фото к проверкам и укусам
клеща, план добавляет файлы анализов и визитов — лимит упрётся молча.

**Подход — заменить только слой персистентности, модель в памяти не трогать:**

- В памяти остаются те же переменные-массивы (`profile`, `entries`, `meds`, `ticks`, `events`, +
  новые `weights`, `qol`) и **весь код рендера работает без изменений**.
- Меняются только `load` / `save` / `drop` / `migrate`: вместо `localStorage`+JSON — IndexedDB.
- Старт становится асинхронным на один шаг: открыть БД → прочитать все стор‑ы в массивы → рендер.
  (ES5-совместимо: IndexedDB — колбэчный API, промисы не обязательны.)
- **Одноразовый импорт:** при первом запуске новой версии `migrate()` читает все существующие
  `misha.*`-ключи из `localStorage`, переносит в IndexedDB, ключи `localStorage` **оставляет на месте**
  как бэкап (не удаляем).
- Медиа (`entry.media`, `photoTick/photoBite`, файлы анализов/визитов) пока остаются dataURL-строками
  внутри записей — просто теперь без лимита. Перевод медиа в отдельный object store с Blob —
  возможное продолжение, в этот заход не обязателен.
- Object stores IndexedDB: по одному на сущность (`profile`, `entries`, `meds`, `ticks`, `events`,
  `weights`, `qol`), плюс `meta` (версия схемы, флаг «импорт из localStorage выполнен»). Новую
  сущность = новый store через bump версии БД и `onupgradeneeded`.

Риск шага 1 максимальный во всём плане (замена слоя хранения в работающем приложении). Поэтому
шаг 1 гейтится критерием приёмки №1 (0.2 п.5) и прогоняется на реальном экспорте до выката.

### 0.3. Требования к миграции (для шага 1 и любых изменений схемы дальше)

1. **Идемпотентность.** Запуск `migrate()` дважды подряд не меняет данные. Каждое новое поле пишется
   только если его нет (`if (x.foo === undefined) x.foo = ...`).
2. **Старый источник не трогаем.** При переезде на IndexedDB (шаг 1) все `misha.*`-ключи в
   `localStorage` оставляем как есть — это бэкап на случай отката. Дальнейшие изменения схемы —
   только через `onupgradeneeded` + версия БД, существующие store-ы не переписываем.
3. **Значения по умолчанию — разумные для истории.** Для существующих `log[]`:
   `date = ISO-день от ts`, `enteredAt = ts`, `isBackdated = false`. Новые поля визита/анализа —
   `undefined` либо пустая строка, код обязан это переваривать.
4. **Проверка на копии реальных данных, не на пустой базе.** Порядок: в работающем приложении
   Профиль → Данные → «Скачать резервную копию» → полученный JSON положить в
   `scratchpad/fixture-real.json` → написать одноразовый node-скрипт, который прогоняет `migrate()`
   над этим объектом и сверяет: число записей в `entries/meds/ticks/events` до = после; каждое
   старое поле читается; повторный прогон не меняет результат.
5. **Критерий приёмки №1 (главный).** Ни одна ранее внесённая запись
   (`profile / entries / meds / ticks / events`) не потеряна и не повреждена. Это важнее, чем
   аккуратность самой новой фичи. Проверяется п. 4 + ручной сверкой в дневнике/лекарствах/календаре
   до и после обновления.

### 0.4. Регрессия на каждом шаге

`node tests.js` (логика статусов) + DOM-смоук-тест (`scratchpad/smoke.js`) + ручной прогон
затронутого экрана. Любой шаг, трогающий `evaluate()` / `RULES` / значения ответов `QUESTIONS`,
обязан обновить `tests.js`.

### A1. Экран «О программе» + дисклеймеры

- **Зачем.** Исследования по киберхондрии прямо рекомендуют: приложение должно честно предупреждать,
  что подобные инструменты могут повышать тревожность, и не претендовать на диагноз. В `PLAN.md` это
  было пунктом T4 и не сделано. Юридический дисклеймер из ТЗ («не медицинское изделие») сейчас

- **Данные.** Нет. Чистый статический экран.
- **Экраны/логика.** Новый `s-about`. Точка входа — строка «О программе» внизу профиля
  (`#s-setup`, карточка «Данные» или отдельная последняя карточка). Содержимое:
  - что это: инструмент наблюдения и организации записей, сравнивает самочувствие с личной нормой Миши;
  - чего не делает: не ставит диагноз, не назначает лечение, не оценивает безопасность лекарств,
    не заменяет очный осмотр;
  - честная фраза про тревожность: «Ежедневные проверки помогают замечать изменения, но у части людей
    частые самопроверки усиливают тревогу. Если чувствуете, что приложение вас накручивает — сократите
    частоту проверок, это нормально»;
  - версия правил (`RULES.version`) и строка «пороги — продуктовые, подтверждаются ветеринаром»;
  - ссылка на резервную копию (дублирует кнопку из «Данные»).
- **evaluate/RULES/tests.** Не затрагивает.
- **Риск.** Нулевой (аддитивный экран).

### A4. Веха «анализ на клещевые инфекции через 4–6 недель» в модуле клеща

- **Зачем.** Вет-источники (AMC, MedVet): симптомы Лайма/эрлихиоза могут проявиться через 7–21 день
  ИЛИ через 2–5 месяцев; врачи часто просят сдать анализ через 4–6 недель после снятия клеща. У нас
  активный контроль авто-завершается ровно на 21-м дне, конкретной вехи с датой нет.
- **Данные.** При сохранении `ticks[]` с `foundAt`/`removedAt`: если у тика нет связанной вехи —
  создать `events` элемент `{ type:"lab", date: base + 35 дней, title:"Обсудить анализ на клещевые
  инфекции", notes:"~4–6 недель после снятия клеща", linkedTickId: tick.id, done:false }`
  (`base = removedAt || foundAt`). Хранить `tick.followUpEventId`, чтобы не плодить дубли при
  повторном сохранении и уметь удалить веху вместе с тиком.
- **Экраны/логика.**
  - Календарь уже агрегирует `events` — веха появится там сама.
  - В карточке тика: строка «Рекомендованный анализ: <дата>» со ссылкой на веху.
  - Смягчить формулировку авто-завершения: не «контроль завершён», а «активная фаза (21 день)
    завершена; следите за самочувствием ещё до ~3 месяцев, при новых признаках — к врачу».
- **evaluate/RULES/tests.** Не затрагивает.
- **Риск.** Низкий; единственная тонкость — не создавать дубль вехи.
- **Порядок.** Шаг 6.

### A6. Счётчик дыхания в покое (SRR) + пороги

- **Зачем.** Вет-кардиология: у здоровой собаки дыхание во сне ≤ 25/мин; устойчиво > 30 — возможен
  отёк лёгких. Сейчас вопрос про дыхание — качественный («спокойно / тяжелее / затруднённо»),
  на глаз. Объективный счётчик делает его измеримым. Особенно полезно, если у Миши есть кардиопатология.
- **Данные.**
  - `profile.trackSRR` (bool, по умолчанию false — фича включается осознанно),
    `profile.srrNorm` (число|null — личная норма вдохов/мин, если снимали в покое).
  - `RULES.srr = { normalMax: 25, concernMin: 30 }` (+ поднять `RULES.version`).
  - в ответах проверки: `answers.srr` (число|null).
- **Экраны/логика.** В вопросе про дыхание (`renderQuestion` для `id:"breathing"`), если
  `profile.trackSRR`:
  - режим «Посчитать»: крупная кнопка, тап на каждый вдох; идёт 30 c, потом ×2 → BPM; показать
    результат и сравнение с `srrNorm` / 25 / 30.
  - качественные варианты остаются как запасной путь и как «не считала».
- **evaluate.** Добавить: `srr >= RULES.srr.concernMin` → red («дыхание в покое N/мин — очень частое»);
  `srr > (srrNorm || RULES.srr.normalMax)` → moderate-признак (в набор «2+ мелочи → жёлтый», рядом с
  «дышит тяжелее обычного»). Качественный `heavy` при наличии числа не дублировать.
- **RULES/tests.** Обновить `RULES.version`; **дописать сценарии в `tests.js`**: srr 34 → red;
  srr 27 при норме 22 → moderate; srr 24 → зелёный; srr 27 + ещё одна мелочь → жёлтый.
- **Риск.** Средний — трогает `evaluate`, поток проверки и тесты. Опциональность (`trackSRR`)
  ограничивает влияние на тех, кто не включил.
- **Порядок.** Шаг 12.

## Часть B. Четыре пункта из присланного ТЗ (адаптировано)

### B1. История обработок задним числом

**Проблема (их формулировка верна и для нас):** формы лекарств/обработок рассчитаны на «отметить
сегодня». Внести обработку, реально сделанную раньше и не заведённую в приложении, нельзя —
`date`-picker в отметке отсутствует, отметка `log[]` пишет только `ts = сейчас`.

**Изменения модели (в наших терминах):**

```
meds[].log[]  элемент:
  { ts,                       // = enteredAt: момент внесения (как сейчас)
    date,                     // NEW: ISO-день фактической обработки/приёма (может быть в прошлом)
    status: "given"|"skipped"|"cancelled",
    isBackdated,              // NEW: true, если |date − день(ts)| > 1 день
    reaction: string|null,    // NEW (опц.)
    note: string|null }       // NEW (опц.)

meds[] элемент:
  ... + oneOff: boolean       // NEW: true — карточка заведена только чтобы держать разовую прошлую запись
      + startDate: string|null   // NEW: для курса, заведённого задним числом
      + intervalDays: number|null // NEW: если задан — «дано» авто-сдвигает nextDate = date + intervalDays
```

Миграция: у всех существующих `log[]` → `date = isoDay(new Date(ts))`, `isBackdated = false`,
`reaction = null`, `note = null`. У всех `meds[]` → `oneOff = false`, `startDate = null`,
`intervalDays = null`. Бамп `misha.meds.v1 → misha.meds.v2` (v1 оставить).

**Форма «Добавить запись задним числом»** (переиспользует поля обычной отметки + date-picker без
нижней границы):

1. Дата — свободный `<input type="date">`, разрешено прошлое.
2. Тип — развилка:
   - **Есть курс** → выбрать из активных `meds[]` → добавить `log[]` с выбранной `date`.
   - **Курса нет** → выбор пользователя (не авто):
     - **«Разовая обработка»** → создать `meds[]` с `oneOff:true`, `kind:"treatment"`,
       `nextDate:null`, `archived:true`, одним элементом `log[]` (`date`, `status:"given"`).
       В дневнике/отчёте показывается как отдельное событие «обработка, разово».
     - **«Завести курс задним числом»** → сокращённая форма создания `meds[]` (название,
       действующее вещество, `startDate = date`, опц. `intervalDays`), сразу с привязанным `log[]`.
       Дальше курс живёт по обычным правилам; `nextDate` считается **от `date`**, не от `enteredAt`.
3. Доза / реакция / заметка — как в обычной отметке.
4. `isBackdated` вычисляется автоматически (граница: ровно 1 день — НЕ backdated; ≥ 2 дня — backdated).
   Влияет только на визуальную пометку «внесено задним числом», не на статус-логику.

**Точки входа:** экран «Лекарства и обработки» → «＋ Запись задним числом»; и та же кнопка в разделе
дневника (см. B2 про объединённую ленту).

**Тест-кейсы:**
- Разовая обработка в прошлом без курса → видна в дневнике, напоминаний не создаёт.
- Обработка в прошлом с созданием курса → `nextDate` считается от `date`.
- `isBackdated`: разница 1 день → false; 2 дня → true.
- Миграция: старые `log[]` получают `date` из `ts`, число записей не изменилось, повторный прогон — no-op.

### B2. История визитов к врачу

**Проблема:** нет сущности «визит как единое целое» (дата + клиника + врач + назначения + файлы +
следующая дата). `events` c `type:"visit"` есть, но там только `date/title/notes/done`.

**Решение — расширить `events` c `type:"visit"`, отдельный стор не заводить** (обоснование — D1):

```
events[] элемент type:"visit":
  { id, type:"visit", date, title, notes, done, createdAt,
    enteredAt,               // NEW
    clinic,                  // NEW: строка (или из profile.clinicName/clinic24Name)
    vetName,                 // NEW
    reason,                  // NEW: плановый / по симптому / повторный
    recommendations,         // NEW: назначения и рекомендации врача (текст)
    prescribedMedIds: [],    // NEW: связь с meds[], если на визите назначен курс
    media: [],               // NEW: файлы/фото (чек, заключение) — та же модель, что entry.media
    followUpDate: null,      // NEW: следующая дата, если назначена
    linkedEntryId: null }    // NEW: если визит открыт с экрана «Результат» жёлтого/красного
```

Миграция: существующие `events` `type:"visit"` дозаполняются пустыми значениями новых полей.
Бамп `misha.events.v1 → misha.events.v2` (v1 оставить).

**Связи:**
- «На визите назначен препарат» → из формы визита открыть сокращённую форму создания `meds[]`
  (та же, что в B1.2 «Завести курс»), с `prescriber = vetName`; id нового курса добавить в
  `prescribedMedIds`.
- `followUpDate` задана → создаётся `events` `type:"visit"` или веха-напоминание на эту дату
  (переиспользует механику B4 / уже существующую агрегацию календаря).
- `linkedEntryId` — на экране результата (`renderResultFoot`) для `status` red/yellow добавить кнопку
  «Записать визит»: открывает форму визита с проставленным `linkedEntryId`. В отчёте это даёт связку
  «жёлтый статус 5-го → визит 7-го».

**Отображение — вариант B (решение принято): дневник НЕ трогаем, визиты/анализы/события живут в
календаре.** `renderDiary` остаётся про здоровье (проверки + прогулки), без изменений. Экран
«Календарь» (`s-calendar`) расширяется в две секции:
- **«Предстоит»** — как сейчас (`calendarItems()`: ближайшая проверка, обработки/прививки с `nextDate`,
  контроль после клеща, будущие визиты и вехи).
- **«История»** — прошедшие `events` (`parseDate(date) ≤ сегодня`): визиты, анализы, заметки —
  сортировка по дате убыв. Строка чипов-фильтров **Всё · Визиты · Анализы · События**. Карточка визита —
  своя иконка/акцентный спокойный цвет.

Плюс переключатель секций вверху экрана (сегментированный «Предстоит / История»). Новый экран не
заводим — переиспользуем `s-calendar` и `calendarItems()`.

**Отчёт (`renderReportView` / `buildReportText`):** новый раздел «Визиты за период» — дата, клиника,
врач, краткие назначения, `followUpDate`. Раздел **не** подчиняется правилу «только отклонения от
нормы» (визит — всегда значимое событие, не сворачивается). Управляется галочкой в
`reportDraft.cats.visits`.

**Тест-кейсы:**
- Создать визит с прошлой датой → виден в «Календарь → История» при фильтре «Визиты» и в отчёте.
- Создать визит с `followUpDate` в будущем → виден в «Календарь → Предстоит».
- Из визита создать курс → курс появляется в «Лекарства», `prescriber` = врач, id в `prescribedMedIds`.
- С экрана красного результата «Записать визит» → `linkedEntryId` сохранён, связка видна в отчёте.
- Миграция: старые `type:"visit"` события читаются, число `events` не изменилось.

### B3. Ручное добавление анализов задним числом

**Проблема:** отдельной формы «внести анализ, сделанный раньше» нет. Анализы сейчас в двух местах:
`events` `type:"lab"` (минимум: `title/notes/date/done`) и `ticks[].analyses[]` (внутри тика).

**Решение — унифицируем (принято): единый стор анализов = `events` `type:"lab"`.
`ticks[].analyses[]` мигрируют сюда в шаге 1.**

```
events[] элемент type:"lab":
  { id, type:"lab", date, title, notes, done, createdAt,
    enteredAt,             // NEW
    labType,               // NEW: тип анализа (заменяет вольный title)
    lab,                   // NEW: лаборатория
    file,                  // NEW: файл результата (та же модель, что media — dataURL/имя)
    result,                // NEW: краткий результат (из tick.analyses[].result)
    vetComment,            // NEW: комментарий врача
    linkedVisitId: null,   // NEW: связь с визитом (B2)
    linkedTickId: null }   // NEW: связь с укусом клеща (A4)
```

**Миграция (шаг 1):**
- существующие `events` `type:"lab"` — новые поля пустые, `labType = title` если был;
- для каждого `ticks[i].analyses[j]` создать `events` `type:"lab"` с `linkedTickId = ticks[i].id`,
  перенести `date/type→labType/lab/result/comment→vetComment`, сгенерировать `id` если не было;
- `ticks[i].analyses` **не удалять сразу** — оставить как есть; код тика после миграции читает анализы
  из `events` по `linkedTickId`, но при пустом результате делает **fallback-чтение** из
  `ticks[i].analyses` (страховка, если миграция что-то пропустила). Через один релиз, убедившись, что
  всё перенеслось — `ticks[i].analyses` можно очищать (отдельный микрошаг).
- флаг `ticks[i]._analysesMigrated = true`, чтобы не дублировать при повторном прогоне.

**Форма «Добавить анализ»** — отдельный экран, точки входа:
1. Календарь → «＋ Добавить анализ» (ни к чему не привязан).
2. Карточка визита (B2) → «Добавить анализ по этому визиту» (проставляет `linkedVisitId`).
3. Карточка укуса клеща → «Добавить анализ» (проставляет `linkedTickId`) — заменяет прежнюю
   inline-форму анализа внутри тика.
4. (после A4) веха «анализ через 4–6 недель» → «Внести результат» (проставляет `linkedTickId`).

Поля: дата анализа (свободная, включая прошлое), тип, лаборатория, файл, краткий результат,
комментарий врача. **Никакой интерпретации результата приложением** (ТЗ п.6).

**Тест-кейсы:**
- Добавить анализ с датой месяц назад → виден в «Календарь → История» (фильтр «Анализы») и в отчёте.
- Добавить анализ из карточки визита → `linkedVisitId` проставлен, в отчёте показан под визитом.
- Добавить анализ из карточки тика → `linkedTickId` проставлен, виден и в карточке тика, и в общем списке.
- Миграция шага 1: все прежние `ticks[].analyses[]` видны как `events` `type:"lab"` с `linkedTickId`,
  ни один не потерян; повторный прогон миграции не создаёт дублей.

### B4. Напоминание за N дней до обработки

**Проблема:** механика доставки напоминаний есть (`scheduleTick` + `.ics`), но нет бизнес-правила
«когда напоминать про обработку/курс».

**Правило:** для каждого `meds[]` где `nextDate` не пусто и `!archived`:
- напоминание на дату `nextDate − offset`, где
  `offset = meds[].reminderOffsetDaysOverride ?? profile.reminderOffsetDays`;
- `profile.reminderOffsetDays` — глобально, дефолт **2** (в `PROFILE_DEFAULTS` + `normalizeProfile`);
- `meds[].reminderOffsetDaysOverride` — число|null, дефолт `null` (в UI формы курса в этот заход
  **можно не выводить** — схема и планировщик уже готовы к per-курсу);
- при изменении `nextDate` (в т.ч. авто-сдвиг после «дано») — старое напоминание не «висит»:
  ключ в `misha.notified` включает `nextDate`, поэтому старый ключ просто перестаёт совпадать.

**Реализация:** в `scheduleTick()` (уже вызывается на старте и раз в 60 c) добавить проход по `meds[]`:
```
для каждого активного meds с nextDate:
  due = parseDate(nextDate) − offset дней
  ключ = "med:" + id + ":" + nextDate
  если сегодня >= due и notified[ключ] не стоит:
    fireNotice("Скоро обработка: " + name + " — " + whenDayText(nextDate))
    notified[ключ] = { at: now }
```
Плюс отражать в календаре (у `treatment`/`vaccine`/`deworming` c `nextDate` уже есть строка — добавить
акцент «напомнить <дата>») и на главной, если до обработки ≤ offset дней.

`.ics` (`buildIcs()`): по желанию добавить VEVENT на каждый `meds.nextDate` c `VALARM TRIGGER:-P{offset}D`.

**Тест-кейсы:**
- Курс с `nextDate` через 2 дня, `offset=2` → напоминание сегодня.
- «Дано» пересчитывает `nextDate` по `intervalDays` → старый ключ не срабатывает, новый создаётся.
- Изменение `profile.reminderOffsetDays` не пересоздаёт уже показанные напоминания — только будущие
  (ключ `misha.notified` по прошлым датам остаётся, новые считаются от нового offset).
- `reminderOffsetDaysOverride = 5` у одного курса → у него напоминание за 5 дней, у остальных за 2.

## Часть D. Решения по спорным местам (обсуждено 07.09.2026)

**D1. Визиты — расширяем `events` c `type:"visit"` (один стор), дневник НЕ смешиваем.**
Решение по 1а — **вариант B**: `renderDiary` остаётся про здоровье (проверки + прогулки), без
изменений. Визиты, анализы и события (прошлые и будущие) живут в экране «Календарь», который получает
две секции — «Предстоит» (как сейчас) и «История» (прошедшие visit/lab/note + чипы-фильтры). Отдельный
стор `vetVisits` не заводим: `events` уже агрегируется одной функцией `calendarItems()`, второй
параллельный стор дал бы вторую точку сборки в календаре и в отчёте. «Толстость» визита закрывается
опциональными полями на `events`-элементе.

**D2. Лаборатории — унифицируем сразу (в шаге 1).**
Единый стор анализов = `events` `type:"lab"`. Все `ticks[].analyses[]` мигрируют туда с
`linkedTickId` в шаге 1; на переходный период код тика делает fallback-чтение из inline-массива
(страховка), сам массив чистим отдельным микрошагом 14 через релиз. Новые анализы (B3) всегда идут в
`events` `type:"lab"`. Отчёт и карточка тика читают анализы из одного места по `linkedTickId`.

**D3. Хранилище — переезжаем на IndexedDB, шаг 1 разбит на 1a/1b/1c.**
Меняется только слой персистентности (`load/save/drop/migrate`), модель в памяти и весь рендер —

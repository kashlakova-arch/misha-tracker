# Misha Health Tracker — план доработки до ТЗ v1.0

Пошаговый план приведения текущего прототипа (`index.html`, один файл, без сборки)
в соответствие с продуктово-техническим заданием.

**Принципы:**
- Один файл `index.html` остаётся способом запуска; сборка не вводится.
- Каждый шаг = отдельное изменение + проверка. Не начинать следующий, пока текущий не проверен.
- Медицинские пороги в коде помечаются версией и комментарием «подтверждается ветеринаром».
- Данные пользователя не теряются: любое изменение схемы localStorage сопровождается миграцией.

**Как проверять каждый шаг:**
1. Открыть `index.html` в браузере, пройти затронутый сценарий вручную.
2. Прогнать `scratchpad/test-logic.js` (сценарии статусов) — все должны быть зелёными.
3. Обновить страницу — данные на месте.

**Обозначения:** ⛒ блокирующий шаг · § — раздел ТЗ · `#anchor` — место в `index.html`.

**Фото Миши:** в корне проекта лежат исходные снимки `2.webp`…`9.webp` (8 шт., присланы хозяйкой).
Это исходники, а не готовые ассеты — их нужно обработать (шаг 0.4) и убрать из корня.
Кадры с людьми (`6.webp`, `9.webp`) — приватные: не публиковать в артефакты/облако, не включать в набор для деплоя, не кэшировать в `sw.js`.

## Слой 1. Корректность логики статусов (1–1.5 дня)

### 1.1. Нейтральный статус «Проверка неполная» ⛒
- **Что:** ввести 4-й статус `neutral`. Правило: красных признаков нет **и** не отвечено
  («не проверяла») по ≥2 из ключевых объективных показателей (моча, дёсны, дыхание) →
  статус `neutral`, без тревожных цветов, серо-нейтральная карточка, действие «Досмотреть Мишу».
- **Зачем:** Приложение A п.4; §5.1.
- **Где:** `evaluate()`; `STATUS_TEXT`; `statusGlyph()`; CSS `.st-neutral` (мягкий серо-бежевый).
- **Сделано, когда:** ответы «не видела/не проверяла» на мочу+дёсны без других сигналов → `neutral`, а не `green`.

### 1.2. Вариант «Не проверяла» на каждом вопросе ⛒
- **Что:** к каждому вопросу проверки добавить нейтральный вариант «Не проверяла / не видела».
  Для мочи и дёсен он уже есть — привести к единому виду. В шкале хромоты добавить кнопку «Не смотрела».
- **Зачем:** §4.2, §8 «кнопка "Не проверяла"»; кормит правило 1.1.
- **Где:** `QUESTIONS`, `renderQuestion()`, `renderLimpQuestion()`.
- **Сделано, когда:** любой вопрос можно пропустить; пропуски видны в дневнике как «не проверялось».

### 1.3. Правило «2+ умеренных признака → жёлтый» ⛒
- **Что:** ввести список умеренных признаков: общее «немного хуже», «съел меньше»,
  «немного сильнее хромает», «однократная рвота», «необычно красные дёсны», «тяжелее обычного дышит».
  Один такой признак — зелёный (как сейчас, с пометкой «в пределах наблюдения»).
  Два и более разных — жёлтый с перечислением.
- **Зачем:** §5 «два и более новых умеренных признака».
- **Где:** `evaluate()` — собирать `moderate[]`, после проверки красных/жёлтых: `if (moderate.length >= 2) status = max(status, "yellow")`.
- **Сделано, когда:** «немного хуже» + «съел меньше» вместе → жёлтый; поодиночке → зелёный.

### 1.4. Аппетит: добавить «съел меньше, но съел»
- **Что:** новый вариант между «ест как обычно» и «пропустил один приём».
- **Зачем:** §4.2 (обычно / съел меньше / пропустил / не ест 24 ч).
- **Где:** `QUESTIONS.appetite.options`, `short`, `evaluate()` (→ умеренный признак из 1.3).
- **Сделано, когда:** вариант выбирается, попадает в дневник и в логику умеренных.

### 1.5. Температура в проверке и в норме
- **Что:**
  - В профиль: поле «Личная нормальная температура, °C» (необязательное) + подсказка «мерить в покое».
  - В проверку: вопрос «Мерили температуру?» → «Не мерила» / ввод значения °C.
  - Логика: `≥ 39.4` при «явно хуже» → жёлтый; `≥ 40.0` при признаках перегрева (новый чек-бокс/вопрос
    «горячий, тяжело дышит после охлаждения») → красный.
- **Зачем:** §3 (блок «Температура»), §5 (пороги 39,4 / 40).
- **Где:** `RULES.temp`, `QUESTIONS`, `evaluate()`, экран профиля.
- **Сделано, когда:** 40,1 °C + перегрев → красный; 39,5 °C + «явно хуже» → жёлтый; 39,5 °C без ухудшения → зелёный.

### 1.6. Недостающие красные признаки
- **Что:** добавить в проверку и в быстрый опрос: «резкая слабость / шаткость», «потеря сознания».
- **Зачем:** §5 (красные условия), §5.1.
- **Где:** `QUESTIONS` (доп. вопрос «Слабость, шаткость, обмороки?»), `QUICK`, `evaluate()`.
- **Сделано, когда:** любой из этих ответов в одиночку → красный.

  - **Температура:** личная норма (из 1.5).

- **Зачем:** §5 (красный: «крупная кнопка звонка… адрес круглосуточной клиники»), §5.1 «не давать лекарственных советов».

- **Сделано, когда:** на каждом статусе одна очевидная кнопка, остальное — второстепенное.

### 2.4. Исправление ответов + журнал изменений

- **Где:** `finishCheck()`, `renderResult()`, `renderDiary()`.
- **Сделано, когда:** правка ответа меняет статус, но в журнале виден исходный ответ и время правки.

- **Сделано, когда:** копия скачивается, восстанавливается на пустом браузере, удаление стирает оба ключа.

## Слой 3. Модули: расписание, лекарства, клещ, календарь, отчёт (3–4 дня)

### 3.1. Расписание проверок и статус «следующая проверка» (§4.1)
- **Что:** в профиле — время двух проверок (по умолчанию 09:00 / 20:00, редактируется).
  На главной — «Следующая проверка — сегодня в 20:00» + отметка, сделана ли она в текущем окне.
  После завершённой проверки в окне — не звать повторно (кроме «Что-то не так»).
- **Зачем:** §4.1, §8 (главная: «следующая проверка»), критерий §13 «два редактируемых напоминания».
- **Где:** профиль; `renderHome()`; хранить `lastCheckWindow`.
- **Сделано, когда:** после утренней проверки главная показывает «Следующая — вечером», кнопка проверки неактивна/вторична до окна.

### 3.2. Напоминания: локальные + резервный календарь ⛒ (честное ограничение)
- **Что:**
  - Пока приложение открыто: `Notification` API + таймеры на время проверок и «через 30 мин» — один мягкий повтор, затем тишина.
  - Резерв (когда push недоступен): кнопка «Добавить напоминания в календарь» → генерация `.ics`
    с двумя ежедневными событиями.
  - Текст уведомлений — из §9 (без тревожных формулировок).
- **Зачем:** §9; ограничение: полноценный Web Push на iPhone требует установленного PWA + серверного push-сервиса — вне рамок одного статического файла. Это фиксируется в README и на экране.
- **Где:** новый модуль `notify` в `<script>`; кнопка в профиле.
- **Сделано, когда:** при открытом приложении приходит локальное уведомление в заданное время; `.ics` импортируется в системный календарь.

### 3.3. Модуль «Лекарства и обработки» (§7)
- **Что:** новый экран + пункт на главной/в календаре. Карточка препарата:
  название, действующее вещество, форма, доза, единицы, время приёма, длительность курса,
  причина, назначивший врач, противопоказания, заметки.
  Отдельный тип — «обработка от клещей/блох» с датой следующей обработки.
  Отметки «дано / пропущено / отменено врачом» — нейтральные формулировки, без чувства вины.
  **Запрет:** никаких авто-рекомендаций дозы/совместимости.
- **Зачем:** §7, критерий §13 «добавляет лекарство и обработку».
- **Где:** новые `KEY_MEDS`, экран `#s-meds`, рендер-функции; связь с календарём (3.5).
- **Сделано, когда:** препарат заводится, отмечается приём, следующая обработка попадает в календарь.

### 3.4. «Напомнить через 3 часа» после жёлтого
- **Что:** кнопка на жёлтом результате ставит локальный таймер + запись в календарь-модуле:
  «повторная проверка Миши».
- **Зачем:** §5 (жёлтый: наблюдать в течение дня), §4.1.
- **Где:** `renderResult()` + модуль `notify`.
- **Сделано, когда:** через 3 часа (или при следующем открытии) появляется напоминание о повторной проверке.

### 3.5. Модуль «Укус клеща» (§6)
- **Что:** карточка события: дата/время обнаружения и удаления, место на теле, наполненность,
  способ удаления, фото клеща и места укуса.
  - Режим активного контроля: 21 день с двумя ежедневными проверками; по истечении —
    автоматически завершается (баннер «режим контроля после клеща завершён»).
  - Долгий контроль: до 3 месяцев — ненавязчивая отметка в истории + напоминание о согласованном анализе.
  - Анализы: дата, тип, лаборатория, файл результата, комментарий врача — **без интерпретации**.
  - Справка: «анализ клеща показывает возбудителя в клеще, но не доказывает заражение собаки».
- **Зачем:** §6, критерий §13 «режим контроля работает 21 день и завершается автоматически».
- **Где:** `KEY_TICKS`, экран `#s-tick`, логика авто-завершения по датам в `renderHome()`.
- **Сделано, когда:** событие создаётся, счётчик «день X из 21» идёт, на 22-й день режим сам гаснет.

### 3.6. Экран «Календарь» (§8)
- **Что:** список/помесячный вид: плановые проверки, курсы лекарств, обработки, визиты,
  контрольные даты (клещ, анализы). Добавление события «визит к врачу» / «анализ».
- **Зачем:** §8.
- **Где:** экран `#s-calendar`, агрегирует данные из meds/ticks/расписания.
- **Сделано, когда:** все будущие даты из других модулей видны в одном списке, отсортированы.

### 3.7. Экран «Отчёт ветеринару» (§10)
- **Что:** выбор периода и категорий → сформировать:
  - период и причина;
  - сводка: сколько зелёных / жёлтых / красных / нейтральных проверок;
  - только изменения относительно нормы (стабильные зелёные дни не дублировать);
  - график веса и температуры (простой SVG/canvas), если данные внесены;
  - лекарства, обработки, пропуски, реакции;
  - на титуле — аватар и кличка Миши (ассет из 0.4); фото/видео по выбранным событиям;
  - блок «Вопросы хозяйки к ветеринару» (свободный ввод, сохраняется).
  Экспорт: печать в PDF (`window.print()` + `@media print` стили), копируемый текст, JSON/CSV.
- **Зачем:** §10, критерий §13 «формируется читаемый отчёт за выбранный период».
- **Где:** экран `#s-report`, `@media print` в CSS.
- **Сделано, когда:** отчёт за «последние 14 дней» печатается в PDF и копируется текстом с корректной сводкой.

### 3.8. Медиа-вложения к проверкам и записям дневника
- **Что:** к обычной проверке и к событиям «после прогулки» разрешить прикрепить фото/видео.
  Управление удалением вложений, ограничение размера, предупреждение о месте в хранилище.
- **Зачем:** §2, §8 (дневник с фото), §11 (файлы, управление удалением).
- **Где:** `finishCheck()`, `renderDiary()`, общий помощник `attachMedia()`.
- **Сделано, когда:** к записи можно приложить фото, оно видно в дневнике и в отчёте, удаляется вручную.

### 3.9. Быстрый лог «После прогулки» (§2)
- **Что:** на главной третья кнопка (или пункт в «Что-то не так») — короткая форма:
  перегрев, моча, клещ (→ создаёт событие 3.5), травма, необычное поведение. Без статуса, просто запись в дневник.
- **Зачем:** §2 (сценарий «После прогулки»).
- **Где:** `#s-quick` расширить режимом, либо новый `#s-walk`.
- **Сделано, когда:** запись о прогулке попадает в дневник и в отчёт, при отметке «клещ» открывается карточка клеща.
